Grails applications can publish an https://www.openapis.org/[OpenAPI] description of their REST
endpoints and browse it with Swagger UI.

springdoc-openapi builds its document from Spring MVC handler methods. Grails dispatches through its
own URL mappings instead, so springdoc on its own produces a document with no paths. The optional
`grails-openapi` module supplies those paths from the application's URL mappings.

==== Getting Started

Add the module, and add the springdoc Swagger UI starter if the browsable UI is also wanted:

[source,groovy]
----
dependencies {
    implementation 'org.apache.grails:grails-openapi'
    implementation 'org.springdoc:springdoc-openapi-starter-webmvc-ui'
}
----

No further configuration is required. springdoc registers its own resource handlers, so Swagger UI
is served even though Grails leaves Spring Boot's catch-all resource handler disabled, and the
springdoc paths fall through the Grails URL mappings because they resolve to no controller.

An application whose URL mappings include a catch-all that resolves to a view or a URI - a
single page application forwarding unmatched paths to an index view, for example - does need to let
the springdoc paths through:

[source,groovy]
----
class UrlMappings {
    static excludes = ['/swagger-ui/**', '/v3/api-docs/**']
}
----

The document is then served from `/v3/api-docs` and the UI from `/swagger-ui/index.html`.

==== What Is Documented

Every URL mapping that names a controller statically becomes a path. A `resources` mapping
contributes each of its generated HTTP methods:

[source,groovy]
----
class UrlMappings {
    static mappings = {
        "/books"(resources: 'book')
    }
}
----

produces `GET` and `POST` on `/books`, and `GET`, `PUT`, `PATCH` and `DELETE` on `/books/{id}`.

URL variables become OpenAPI path parameters, so `"/books/$id"` is documented as `/books/{id}`. The
optional `.format` extension Grails appends to REST mappings is omitted, because OpenAPI describes
response formats through content types rather than the path.

==== Domain Schemas

A domain class served by a documented path is described in `components/schemas`, built from the GORM
mapping model. Associations are referenced rather than inlined, so a `Book` with `hasMany` readers
refers to the `User` schema, and an associated class is defined even when it has no documented path
of its own. A domain class that nothing documented refers to is left out.

The identifier and the version are marked `readOnly`, because the server assigns them. Tools that
understand OpenAPI leave a read-only property out of a request body, so one schema describes both
directions.

Declared constraints are carried across:

[cols="1,1"]
|===
| Constraint | OpenAPI

| `nullable: false` | listed in `required`
| `maxSize` / `size` | `maxLength` and `minLength`
| `min` / `max` / `range` | `minimum` and `maximum`
| `inList` | `enum`
| `matches` | `pattern`
| `email` / `url` | `format`
|===

A domain class without a constraints block still produces a schema; it simply carries no
validation facets.

Operations addressed by an identifier also document a `404` response.

==== Controllers Reached Through the Default Mapping

A `RestfulController` is also served by the default `"/$controller/$action?/$id?"` mapping, at URLs
such as `/book/show/1`. Those routes answer whether or not a mapping names the controller, so they
are documented too, with the id segment on the actions that address a single resource and the method
each action declares through `allowedMethods`:

----
GET    /book/index          POST   /book/save
GET    /book/show/{id}      PUT    /book/update/{id}
GET    /book/create         PATCH  /book/patch/{id}
GET    /book/edit/{id}      DELETE /book/delete/{id}
----

A controller named by a `resources` mapping is therefore described twice, once at `/books/{id}` and
once at `/book/show/{id}`, because both answer. An endpoint that responds but is absent from the
document is worse than one described twice: the document is used to review the surface an
application actually exposes, not only to browse it. An application that wants only the first form
should remove the default mapping from `UrlMappings.groovy`.

Only `RestfulController` subclasses are described this way, so a controller rendering GSP views does
not appear in the document. This includes controllers generated by scaffolding, which extend
`RestfulController`.

One kind of mapping is not documented in full:

* A mapping that accepts any HTTP method is documented as `GET`, because OpenAPI requires a
  concrete operation.

==== Customizing the Document

The module contributes paths through the springdoc `OpenApiCustomizer` interface, and applications
can register further customizers of their own. Document level information is configured the usual
springdoc way:

[source,yaml]
----
springdoc:
    api-docs:
        path: /v3/api-docs
    swagger-ui:
        path: /swagger-ui.html
----
