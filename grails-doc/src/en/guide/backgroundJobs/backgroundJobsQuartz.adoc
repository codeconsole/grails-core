The Quartz plugin adds a `Job` artefact type to Grails, backed by the https://www.quartz-scheduler.org/[Quartz Enterprise Job Scheduler]. Compared to `@Scheduled` it gives you a schedule you can change, inspect, pause, and persist at runtime — and, most importantly, one that can be coordinated across a cluster.

Add it to `build.gradle`; the version is managed by the Grails BOM:

[source,groovy]
----
dependencies {
    implementation 'org.apache.grails:grails-quartz'
}
----

A job is a class in `grails-app/jobs` whose name ends in `Job`, with an `execute` method and a `triggers` block:

[source,groovy]
----
package myapp

class DigestJob {

    ReportService reportService

    static triggers = {
        cron name: 'dailyDigest', cronExpression: '0 0 6 * * ?'
    }

    void execute() {
        reportService.sendDailyDigest()
    }
}
----

Jobs are Spring beans autowired by name, so services inject exactly as they do in a controller.

===== What the plugin adds over `@Scheduled`

* *Multiple triggers per job*, mixing interval-based and cron-based schedules on the same unit of work.
* *Runtime scheduling* — `DigestJob.schedule(...)`, `DigestJob.triggerNow(...)`, `DigestJob.unschedule(...)` — so schedules can be driven by data rather than fixed at compile time.
* *A `jobManagerService`* for listing, pausing, resuming, and interrupting jobs and triggers while the application runs.
* *Persistence*, so a schedule survives a restart rather than being rebuilt from annotations.
* *Clustering*, covered in <<backgroundJobsClustering,Clustered Jobs>>.
* *Hibernate session binding*, so a job can use GORM the way a service does.

The full reference — every trigger attribute, job property, and configuration option — is in the xref:quartz.adoc#quartz[Quartz] chapter.

===== Choosing between the two

Reach for `@Scheduled` when the schedule is fixed, the application runs as a single instance, and the work is short. Reach for Quartz when any of those stops being true: when operators need to pause a job, when the schedule comes from configuration or data, when a missed run has to be recovered, or when more than one instance is deployed.

Nothing prevents using both in the same application — they are independent schedulers — but a given piece of work should belong to exactly one of them.
