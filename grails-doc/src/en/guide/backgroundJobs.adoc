Most applications eventually need work to happen on a schedule rather than in response to a request: sending a nightly digest, expiring stale records, polling an upstream feed, rebuilding a cache.

Grails offers two approaches, and the right one depends almost entirely on how many instances of your application will be running:

[cols="1,3,3"]
|===
| | Spring `@Scheduled` | <<backgroundJobsQuartz,Quartz>>

| Setup
| Built in — nothing to add
| Add the `grails-quartz` plugin

| Where the schedule lives
| An annotation on a bean method
| A `triggers` block on a job artefact

| Changing the schedule at runtime
| Not supported
| Supported

| Persistent across restarts
| No
| Optional, with a JDBC job store

| Safe to run on multiple instances
| *No* — every instance fires independently
| Yes, with clustering enabled

| Pausing, resuming, inspecting jobs
| Not supported
| Supported
|===

The short version: if your application runs as a single instance, `@Scheduled` is the simpler choice and needs no dependencies. As soon as you run more than one instance — a scaled deployment, a rolling restart, a blue/green cutover — you need <<backgroundJobsClustering,coordination between the instances>>, and that is what Quartz provides.

WARNING: The most common production surprise with background jobs is a schedule written when the application ran on one machine, later deployed to three. Nothing fails loudly; the job simply runs three times. See <<backgroundJobsClustering,Clustered Jobs>>.
