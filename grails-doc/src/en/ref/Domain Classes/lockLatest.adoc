== lockLatest

=== Purpose

Reloads an already-loaded entity's database state and version directly under a pessimistic WRITE lock, refreshing the same instance. Supported by GORM for Hibernate 5 and Hibernate 7.

=== Examples

[source,groovy]
----
Book.withTransaction {
    def book = Book.get(1)
    book.lockLatest()
    if (book.title == 'Draft') {
        book.title = 'Ready for review'
        book.save(failOnError: true)
    }
}
----

=== Description

The dedicated instance method `entity.lockLatest()` reloads state and version into the same entity instance using a single refresh-with-lock operation. It is not two separate calls to `lock()` and `refresh()` in either order. It reloads the version rather than trying to lock using the already-loaded version.

An active transaction is required. Use link:{domainClassesRefFromRef}withTransaction.html[withTransaction] as above or a GORM `@Transactional` method, and keep the lock and the work it protects in the same transaction. The lock is held until that transaction commits or rolls back. Calling `lockLatest()` without an active transaction throws `jakarta.persistence.TransactionRequiredException`.

The instance must be attached to the current session. Calling `lockLatest()` on a detached instance fails; re-attach it with link:{domainClassesRefFromRef}attach.html[attach] or reload it first.

WARNING: `lockLatest()` discards unflushed changes to the entity. Configured refresh cascades can also discard unflushed changes to associated entities; this is not a refresh of the whole object graph. Call it *before* making decisions based on the entity's state or applying mutations. It does not preserve or merge pending edits.

The database and transaction isolation level determine which state is visible to the locked refresh. Despite its name, `lockLatest()` does not override isolation rules or guarantee that every concurrent attempt succeeds. Deadlocks, lock timeouts, and transaction serialization failures remain possible. Ordinary reads are not necessarily blocked by a write lock.

The same operation is available wherever GORM exposes instance operations, so it can also be used on a named connection or under a bound tenant:

[source,groovy]
----
Book.withTransaction {
    def book = Book.get(1)
    book.secondary.lockLatest()     // <1>
}
----
<1> Reloads and locks the row on the `secondary` connection.

The method is supported by GORM for Hibernate 5 and Hibernate 7. Datastores that do not support `lockLatest()` throw `UnsupportedOperationException` rather than silently falling back to a non-refreshing lock.

The existing link:{domainClassesRefFromRef}lock.html[lock()] method is unchanged: it does not reload state and still checks the version of an already-loaded, versioned entity, so a concurrent update can cause an optimistic locking failure. The static `DomainClass.lock(id)` method is also unchanged and does not guarantee a refresh if the entity is already managed in the current session. Use `lockLatest()` when that same instance needs to be reloaded under a write lock.
